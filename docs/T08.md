# T08 — 내 소개 페이지에 패스키 달기

## 1. 구현 요약

T01 공개 자기소개 페이지는 그대로 공개하고 `/private`만 패스키(WebAuthn) 인증 뒤 서버 API에서 비공개 자료를 내려받습니다.

- 비밀번호: 사용하지 않음
- 브라우저 인증: WebAuthn `navigator.credentials.create/get`
- 등록/인증 알고리즘: ES256 / P-256
- DB: Supabase PostgreSQL
- Supabase 접근: 서버 전용 Secret Key 우선 사용, legacy `service_role` 키 fallback 지원
- 세션: 32바이트 랜덤 토큰을 HttpOnly 쿠키로 발급하고 DB에는 SHA-256 해시만 저장
- challenge: 서버에서 32바이트 랜덤 값 생성, DB에 5분간 저장, 검증 시 원자적으로 삭제
- 비공개 자료: 로그인 세션의 사용자 ID로만 조회
- 실제 개인정보: 사용하지 않음. 초기 계정 생성 시 과제용 가상 메모 3개 생성

## 4. 로컬 환경 변수

`.env.example`을 참고해 프로젝트 루트에 `.env.local`을 만듭니다.

새 Supabase Secret Key를 사용하는 경우:

```env
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_SECRET_KEY=sb_secret_YOUR_SECRET_KEY
WEBAUTHN_RP_ID=localhost
WEBAUTHN_ORIGIN=http://localhost:3001
WEBAUTHN_RP_NAME=Odyz Developer Profile
```

현재 검증 환경처럼 legacy `service_role` 키를 사용하는 경우에는 `SUPABASE_SECRET_KEY` 대신 다음 변수를 사용합니다.

```env
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_SERVICE_ROLE_KEY=YOUR_LEGACY_SERVICE_ROLE_KEY
WEBAUTHN_RP_ID=localhost
WEBAUTHN_ORIGIN=http://localhost:3001
WEBAUTHN_RP_NAME=Odyz Developer Profile
```

실제 legacy `service_role` 값을 `SUPABASE_SECRET_KEY` 변수에 넣으면 새 Secret Key 방식으로 오인해 `Authorization: Bearer` 헤더가 빠질 수 있으므로 키 종류와 변수명을 일치시킵니다.

둘 다 설정되어 있으면 `SUPABASE_SECRET_KEY`를 우선 사용합니다. 새 `sb_secret_...` 키는 서버 REST 요청에서 `apikey` 헤더로 사용하고, legacy `service_role` JWT fallback은 `apikey`와 `Authorization: Bearer` 헤더를 함께 사용합니다.

## 5. Production 환경 변수

Production URL이 `https://aleph-t01.vercel.app`이라면 Vercel에 다음 값을 설정합니다.

legacy `service_role` 키를 계속 사용하는 현재 환경:

```text
SUPABASE_URL=<Supabase Project URL>
SUPABASE_SERVICE_ROLE_KEY=<Legacy service_role Key>
WEBAUTHN_RP_ID=aleph-t01.vercel.app
WEBAUTHN_ORIGIN=https://aleph-t01.vercel.app
WEBAUTHN_RP_NAME=Odyz Developer Profile
```

새 `sb_secret_...` 키를 발급한 경우에는 `SUPABASE_SERVICE_ROLE_KEY` 대신 `SUPABASE_SECRET_KEY`를 설정합니다. 서버 전용 키는 저장소나 브라우저로 전달하지 않습니다.

WebAuthn은 RP ID와 Origin이 정확히 일치해야 하므로 Preview Deployment의 임시 도메인에서는 실패할 수 있습니다. 최종 검증은 Production 도메인에서 진행합니다.

또한 `localhost`에서 만든 credential은 RP ID가 `localhost`에 묶여 있으므로 Production RP ID인 `aleph-t01.vercel.app`에서 재사용할 수 없습니다. Production 검증용 패스키는 Production 도메인에서 새로 등록합니다.

## 6. 실제 검증에 사용한 패스키 저장 위치

외부 휴대폰·USB 보안키·Windows Hello 대신 **Chrome DevTools의 WebAuthn Virtual Authenticator**를 사용합니다.

가상 인증기 설정:

```text
Protocol: ctap2
Transport: internal
Supports resident keys: enabled
Supports user verification: enabled
```

로컬 검증 계정 A:

```text
username: test
display name: test
passkey 1 label: test
passkey 2 label: test-2
```

두 패스키는 서로 다른 Virtual Authenticator에 저장해 서로 다른 credential로 생성했습니다.

```text
Virtual Authenticator A
- credential: test

Virtual Authenticator B
- credential: test-2
```

따라서 T08의 패스키 저장 위치 기록은 다음과 같이 작성합니다.

> Chrome DevTools WebAuthn Virtual Authenticator의 CTAP2/internal 가상 인증기에 저장했다. 첫 번째와 두 번째 패스키는 서로 다른 가상 인증기에 저장해 서로 다른 credential로 검증했다.

Virtual Authenticator는 실제 물리 보안 장치가 아니라 개발·검증용 WebAuthn 에뮬레이터입니다. 이 사실을 숨기지 않고 제출 설명에 명시합니다.

Production 검증에서는 `aleph-t01.vercel.app` RP ID에 맞는 credential을 새로 등록해야 합니다. 로컬 `test` 계정과 충돌하지 않도록 Production에서는 별도 계정 이름을 사용하는 편이 안전합니다.

## 7. 브라우저에서 직접 확인할 항목

1. 계정 A 첫 패스키 등록
2. 계정 A 로그인 상태에서 두 번째 Virtual Authenticator로 두 번째 패스키 등록
3. 패스키 2개의 이름과 등록 날짜 확인
4. 계정 B를 별도 이름/표시 이름으로 생성해 계정 A와 다른 비공개 내용 생성
5. 패스키 등록을 중간에 취소하고 취소 안내 및 DB 미저장 확인
6. 계정 A 패스키 하나 삭제
7. 삭제된 Virtual Authenticator credential 로그인 실패 확인
8. 남은 Virtual Authenticator credential 로그인 성공 확인
9. Production 도메인에서는 Production RP ID용 credential을 새로 등록해 동일 흐름 재검증

## 8. 필수 검증 기록

### 8-1. 로그인하지 않고 비공개 API 요청

```js
fetch('/api/private').then(async (r) => ({
  status: r.status,
  body: await r.json(),
}))
```

예상:

```text
401 LOGIN_REQUIRED
```

### 8-2. challenge 값이 매번 다른지 확인

로그인 옵션 요청을 두 번 실행합니다.

```js
Promise.all([
  fetch('/api/passkeys/authenticate/options', { method: 'POST' }).then((r) => r.json()),
  fetch('/api/passkeys/authenticate/options', { method: 'POST' }).then((r) => r.json()),
]).then(([a, b]) => ({
  challengeA: a.publicKey.challenge,
  challengeB: b.publicKey.challenge,
  different: a.publicKey.challenge !== b.publicKey.challenge,
}))
```

`different: true`여야 합니다.

등록 challenge도 `/api/passkeys/register/options`를 서로 다른 미등록 계정 이름으로 두 번 호출해 서로 다른 challenge인지 확인하고, 검증하지 않을 challenge는 `/api/passkeys/challenge/cancel`로 정리합니다.

### 8-3. 사용한 challenge 재사용

성공한 `/api/passkeys/authenticate/verify` 요청 본문을 같은 값으로 다시 전송합니다.

예상:

```text
400 CHALLENGE_INVALID_OR_USED
```

### 8-4. 잘못된 서명

새 로그인 challenge의 인증 응답에서 `signature` 일부를 변조해 검증 API로 보냅니다.

예상:

```text
401 SIGNATURE_VERIFICATION_FAILED
```

그 다음 새 challenge로 정상 로그인을 수행해 성공 요청도 함께 남깁니다.

### 8-5. 로그아웃 뒤 세션 재사용

로그인 상태의 `t08_session` 쿠키 값은 증거 기록에서 반드시 가립니다. 로그아웃 후 기존 쿠키 값으로 `/api/session` 또는 `/api/private`를 다시 요청합니다.

예상:

```text
401 LOGIN_REQUIRED
```

로그아웃 시 DB의 `t08_sessions` 행을 삭제하므로 기존 쿠키 문자열만 복원해도 세션이 살아나지 않아야 합니다.

### 8-6. 계정 A에서 계정 B 자료 직접 요청

계정 A 로그인 상태에서:

```js
fetch('/api/private/<ACCOUNT_B_USER_ID>').then(async (r) => ({
  status: r.status,
  body: await r.json(),
}))
```

예상:

```text
403 FORBIDDEN_OTHER_USER
```

계정 B에서도 계정 A ID를 넣어 반대 방향을 동일하게 검증합니다.

### 8-7. 요청에 다른 userId를 넣어도 세션 사용자의 자료만 반환

```js
fetch('/api/private?userId=<ACCOUNT_B_USER_ID>').then((r) => r.json())
```

계정 A 로그인 상태라면 응답 `owner.id`는 A여야 하고 `requestedUserIdIgnored`는 `true`여야 합니다.

### 8-8. 비공개 내용이 HTML에 없는지 확인

로그아웃 상태에서 `/private` 페이지 소스를 확인합니다. DB의 가상 비공개 항목 제목과 본문이 HTML 응답에 포함되어 있지 않아야 합니다. 비공개 내용은 로그인 성공 뒤 `/api/private`에서만 내려옵니다.

## 9. 서버에 저장되는 패스키 값

`t08_passkeys`에는 다음만 저장합니다.

- credential ID
- 공개키 JWK
- signature counter
- 패스키 이름
- 등록 시각

개인키는 등록 요청 본문에 포함되지 않고 서버로 전송하거나 저장하지 않습니다.

## 10. 패스키 삭제 정책

마지막 패스키 삭제는 `LAST_PASSKEY_PROTECTED`로 거절합니다. 패스키가 두 개 이상일 때만 하나를 삭제할 수 있습니다.

검증 순서:

1. A 패스키 1 등록
2. A 패스키 2 등록
3. 둘 다 목록에 표시되는지 확인
4. 하나 삭제
5. 삭제된 credential 로그인 실패
6. 남은 credential 로그인 성공
7. 마지막 남은 패스키 삭제 시도는 `409 LAST_PASSKEY_PROTECTED` 확인

## 11. 아직 못 막은 것과 검증 환경의 한계

현재 구현은 `attestation: none`을 사용합니다. RP ID hash, origin, challenge, 사용자 검증 플래그, 공개키, 로그인 서명은 확인하지만 인증기 제조사나 특정 승인 기기 여부를 attestation 인증서 체인으로 검증하지 않습니다.

모든 실제 패스키 보관 기기를 동시에 분실한 경우 별도 계정 복구 절차도 없습니다. 마지막 서버 등록 패스키 삭제는 막지만 기기 자체를 모두 분실한 경우 복구할 수 없습니다.

또한 현재 기능 검증은 Chrome DevTools Virtual Authenticator를 사용합니다. WebAuthn challenge/credential/서명/삭제 흐름은 실제 브라우저 API로 검증할 수 있지만, 물리 보안 키 분실이나 실제 기기 간 동기화 같은 현실의 장치 운용까지 검증하는 것은 아닙니다.

만료된 challenge/session 행은 조회 시 인증에 사용할 수 없지만 별도 주기적 정리 작업은 아직 없습니다. 인증 옵션 생성 API에 별도 rate limit도 적용하지 않았습니다.

## 12. 인증 구현 설명서 여섯 항목 초안

### ① 무엇으로 붙였나

브라우저 표준 WebAuthn API와 Next.js Route Handler를 사용해 패스키 인증을 직접 구현했습니다. DB는 Supabase PostgreSQL을 사용하고, 서버 전용 키로만 DB REST/RPC에 접근합니다. 비밀번호와 OAuth는 사용하지 않습니다. 기능 검증용 인증기는 Chrome DevTools WebAuthn Virtual Authenticator를 사용했습니다.

### ② 왜 그걸 골랐나

공개키/개인키, 서버 challenge, 서명 검증, challenge 재사용 차단을 코드와 요청/응답에서 직접 확인하기 위해 WebAuthn 흐름을 분리해 구현했습니다. Supabase는 인증 서비스가 아니라 서버 저장소로만 사용합니다. Virtual Authenticator는 외부 장치 없이 서로 다른 credential 두 개와 삭제/실패 시나리오를 재현하기 위해 선택했습니다.

### ③ 어디를 어떻게 고쳤나

등록은 `register/options`와 `register/verify`, 로그인은 `authenticate/options`와 `authenticate/verify`, 로그아웃은 `/api/logout`, 비공개 자료 조회는 `/api/private`를 통과합니다. WebAuthn 검증은 `src/lib/t08/webauthn.ts`, 서버 세션은 `src/lib/t08/session.ts`, Supabase 서버 접근은 `src/lib/t08/db.ts`에 있습니다.

### ④ 안 열리는 것을 확인한 기록

Production 환경에서 다음 네 가지 성공/실패 요청을 캡처해 제출문에 기록합니다.

- 로그인 없이 `/api/private`
- 계정 A/B 상호 자료 접근
- 사용한 challenge 재전송
- 패스키 삭제 후 삭제된 credential 로그인

### ⑤ AI와 나

AI는 요구사항 분해, WebAuthn/API/DB 구조 설계, 코드 정적 검증과 테스트 절차 설계를 담당했습니다. 사용자는 실제 브라우저에서 Virtual Authenticator 등록/전환, Supabase 결과 확인, Production 배포와 최종 화면 캡처를 직접 수행했습니다.

### ⑥ 아직 못 막은 것

`attestation: none`이므로 인증기 제조사나 승인 기기 여부까지 검증하지 않습니다. 모든 패스키 보관 기기를 동시에 분실한 경우 별도 복구 절차가 없습니다. 또한 가상 인증기 기반 기능 검증은 실제 물리 장치의 분실·동기화 동작까지 증명하지 않습니다.

## 13. 로컬 정적 검증

환경변수를 설정한 뒤 다음을 실행합니다.

```bash

npx tsc --noEmit
npm run build
```

현재 로컬에서는 3000 포트를 다른 서비스가 사용하므로 개발 서버를 3001로 실행합니다.

```bash
npm run dev -- -p 3001
```

이 경우 `.env.local`의 `WEBAUTHN_ORIGIN`도 반드시 다음과 일치해야 합니다.

```text
WEBAUTHN_ORIGIN=http://localhost:3001
```

공개 페이지와 `/private`를 확인한 뒤 WebAuthn Virtual Authenticator 검증으로 넘어갑니다.
