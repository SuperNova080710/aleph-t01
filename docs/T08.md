# T08 — 내 소개 페이지에 패스키 달기

## 1. 구현 요약

T01 공개 자기소개 페이지는 그대로 공개합니다. `/private`만 패스키(WebAuthn) 인증 뒤 서버 API에서 비공개 자료를 내려받습니다.

- 비밀번호: 사용하지 않음
- 브라우저 인증: WebAuthn `navigator.credentials.create/get`
- 등록 알고리즘: ES256 / P-256
- DB: Supabase PostgreSQL
- 세션: 32바이트 랜덤 토큰을 HttpOnly 쿠키로 발급하고, DB에는 SHA-256 해시만 저장
- challenge: 서버에서 32바이트 랜덤 값 생성, DB에 5분간 저장, 검증 시 원자적으로 삭제
- 비공개 자료: 로그인 세션의 사용자 ID로만 조회
- 실제 개인정보: 사용하지 않음. 초기 계정 생성 시 과제용 가상 메모 3개를 서버에서 생성

## 3. 사용자가 직접 해야 하는 초기 설정

### 3-1. Supabase 프로젝트

T08 전용 Supabase 프로젝트를 하나 만드는 것을 권장합니다. 프로젝트를 만든 뒤 SQL Editor에서 `supabase/t08.sql` 전체를 실행합니다.

브라우저에는 Supabase 키를 넣지 않습니다. `SUPABASE_SERVICE_ROLE_KEY`는 서버 환경 변수에만 둡니다.

### 3-2. 로컬 환경 변수

`.env.example`을 참고해 `.env.local`을 만듭니다.

```env
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVICE_ROLE_KEY
WEBAUTHN_RP_ID=localhost
WEBAUTHN_ORIGIN=http://localhost:3000
WEBAUTHN_RP_NAME=Odyz Developer Profile
```

### 3-3. Vercel 환경 변수

배포 도메인이 `https://aleph-t01.vercel.app`이라면 다음 값으로 등록합니다.

```text
SUPABASE_URL=<Supabase Project URL>
SUPABASE_SERVICE_ROLE_KEY=<Supabase service_role key>
WEBAUTHN_RP_ID=aleph-t01.vercel.app
WEBAUTHN_ORIGIN=https://aleph-t01.vercel.app
WEBAUTHN_RP_NAME=Odyz Developer Profile
```

Preview Deployment의 임시 도메인은 RP ID가 달라 WebAuthn이 실패할 수 있으므로 최종 검증은 Production 도메인에서 합니다.

## 4. 권장 테스트 계정/패스키 이름

실제 개인정보를 넣지 않습니다.

```text
계정 A
username: odyz-demo-a
display name: 테스트 계정 A
passkey 1: Windows Hello
passkey 2: Phone Passkey

계정 B
username: odyz-demo-b
display name: 테스트 계정 B
passkey 1: Account B Passkey
```

계정 A의 두 번째 패스키는 첫 번째 패스키와 **다른 credential**이어야 합니다. 같은 플랫폼 인증기가 중복 등록을 막으면 휴대폰, 다른 패스키 저장소 또는 보안 키를 사용합니다.

## 5. 실제 기기에서 반드시 직접 해야 하는 항목

코드만으로 증명할 수 없으므로 다음은 실제 브라우저/기기에서 수행하고 증거를 남깁니다.

1. 계정 A 첫 패스키 등록
2. 계정 A 로그인 상태에서 두 번째 패스키 등록
3. 등록된 패스키 2개의 이름과 등록 날짜 화면 캡처
4. 계정 B를 별도로 만들고 패스키 등록
5. 패스키 창에서 등록을 한 번 취소하고 취소 안내 확인
6. 계정 A의 패스키 하나 삭제
7. 삭제된 패스키 로그인 실패 확인
8. 남은 패스키 로그인 성공 확인
9. 패스키가 실제로 저장된 곳 기록
   - 예: Windows Hello / Google Password Manager / Android 기기 / 보안 키

## 6. 필수 검증 기록

### 6-1. 로그인하지 않고 비공개 API 요청 — 401

새 시크릿 창에서 DevTools Console 또는 터미널로 확인합니다.

```js
fetch('/api/private').then(async (r) => ({
  status: r.status,
  body: await r.json(),
}))
```

예상:

```json
{
  "status": 401,
  "body": {
    "error": {
      "code": "LOGIN_REQUIRED"
    }
  }
}
```

### 6-2. challenge가 매번 다른지 확인

로그인 옵션 요청을 두 번 실행해 `challenge`가 다른지 기록합니다.

```js
Promise.all([
  fetch('/api/passkeys/authenticate/options', { method: 'POST' }).then((r) => r.json()),
  fetch('/api/passkeys/authenticate/options', { method: 'POST' }).then((r) => r.json()),
]).then(([a, b]) => ({
  challengeA: a.publicKey.challenge,
  challengeB: b.publicKey.challenge,
  different: a.publicKey.challenge !== b.publicKey.challenge,
}))
```

등록 challenge도 `/api/passkeys/register/options` 응답 두 건을 비교합니다.

### 6-3. 이미 사용한 challenge 재사용 — 400

DevTools Network에서 성공한 `/api/passkeys/authenticate/verify` 요청의 요청 본문을 보관합니다. 같은 본문을 다시 전송합니다.

예상 코드:

```text
400 CHALLENGE_INVALID_OR_USED
```

실제 제출문에서는 challenge 전체 값을 그대로 공개하지 않아도 됩니다.

### 6-4. 잘못된 서명 — 401

새 로그인 challenge를 받은 뒤 인증 요청의 `signature` 일부를 변경해 `/api/passkeys/authenticate/verify`로 보냅니다.

예상 코드:

```text
401 SIGNATURE_VERIFICATION_FAILED
```

그 다음 새 challenge로 정상 로그인하여 성공 요청도 함께 남깁니다.

### 6-5. 로그아웃 뒤 같은 세션 재사용 — 401

로그인 상태에서 `t08_session` 쿠키 값을 DevTools로 확인한 뒤 기록에는 반드시 가립니다. 로그아웃 후 예전 쿠키를 별도 요청에 다시 넣어 `/api/session` 또는 `/api/private`를 호출합니다.

예상:

```text
401 LOGIN_REQUIRED
```

DB의 `t08_sessions` 행은 로그아웃 때 삭제되므로 쿠키 문자열만 복원해도 세션이 살아나지 않습니다.

### 6-6. 계정 A → 계정 B 자료 접근 — 403

각 계정의 `/api/session` 응답에서 사용자 ID를 기록합니다.

계정 A로 로그인한 상태에서:

```js
fetch('/api/private/<ACCOUNT_B_USER_ID>').then(async (r) => ({
  status: r.status,
  body: await r.json(),
}))
```

예상:

```text
403 FORBIDDEN_OTHER_USER
```

계정 B로 로그인한 뒤 A ID를 넣어 반대 방향도 동일하게 확인합니다.

거절 전후 각 계정에서 `/api/private`의 `items.length`를 기록해 자료 건수가 변하지 않았음을 남깁니다.

### 6-7. 요청에 다른 userId를 넣어도 내 자료만 반환

계정 A 로그인 상태에서:

```js
fetch('/api/private?userId=<ACCOUNT_B_USER_ID>').then((r) => r.json())
```

응답의 `owner.id`는 A이고 `requestedUserIdIgnored`는 `true`여야 합니다.

### 6-8. 비공개 내용이 HTML에 포함되지 않는지 확인

로그아웃 상태에서 `/private`의 페이지 소스를 확인합니다. DB에서 생성된 다음과 같은 실제 가상 메모 본문은 HTML에 없어야 합니다.

```text
테스트 계정 A 계정용 가상 메모: ...
테스트 계정 B 계정용 가상 메모: ...
```

비공개 내용은 로그인 후 `/api/private` 응답에서만 내려옵니다.

## 7. 서버에 저장되는 값

`t08_passkeys`에는 다음을 저장합니다.

- credential ID
- 공개키 JWK (`P-256`의 x/y 공개 좌표)
- signature counter
- 사용자가 붙인 패스키 이름
- 등록 시각

**개인키는 등록 요청 본문에 존재하지 않으며 서버로 전송되거나 저장되지 않습니다.** 개인키는 패스키 저장소/인증기 쪽에 남습니다.

## 8. 패스키 삭제 정책

마지막 패스키를 삭제하면 계정에 다시 들어갈 방법이 없어지므로 서버가 `LAST_PASSKEY_PROTECTED`로 거절합니다. 패스키가 두 개 이상일 때만 하나를 삭제할 수 있습니다.

따라서 과제 검증은 다음 순서로 합니다.

1. A 패스키 1 등록
2. A 패스키 2 등록
3. 둘이 목록에 있는지 확인
4. 하나 삭제
5. 삭제된 credential 선택 시 로그인 실패
6. 남은 credential로 로그인 성공

## 9. 아직 못 막은 것

이 구현은 `attestation: none`을 사용하고 RP ID hash, origin, challenge, 사용자 검증 플래그, credential 공개키, 로그인 서명을 검증합니다. 그러나 **인증기 제조사/기기 신뢰도를 증명하는 attestation 인증서 체인은 검증하지 않습니다.** 따라서 등록된 패스키가 특정 승인 기기에서 생성되었다는 것까지 보증하지는 않습니다.

또한 계정의 모든 실제 패스키 저장소를 동시에 잃어버린 경우를 위한 별도 계정 복구 절차는 제공하지 않습니다. 마지막 서버 등록 패스키 삭제는 막지만, 기기 자체를 모두 분실한 경우 복구할 수 없습니다.

## 10. 인증 구현 설명서 여섯 항목 초안

### ① 무엇으로 붙였나

브라우저 표준 WebAuthn API와 Next.js Route Handler를 사용해 패스키 인증을 직접 구현했습니다. DB는 Supabase PostgreSQL을 사용합니다. 비밀번호와 OAuth는 사용하지 않습니다.

### ② 왜 그걸 골랐나

T08의 핵심인 공개키/개인키, 서버 challenge, 서명 검증, challenge 재사용 차단을 코드에서 직접 확인하기 위해 WebAuthn 흐름을 분리해서 구현했습니다. Supabase는 인증 서비스가 아니라 서버 저장소로만 사용합니다.

### ③ 어디를 어떻게 고쳤나

등록은 `register/options`와 `register/verify`, 로그인은 `authenticate/options`와 `authenticate/verify`, 로그아웃은 `/api/logout`, 비공개 자료 조회는 `/api/private`를 통과합니다. WebAuthn 검증은 `src/lib/t08/webauthn.ts`, 서버 세션은 `src/lib/t08/session.ts`에 있습니다.

### ④ 안 열리는 것을 확인한 기록

제출 직전에 실제 Production 환경에서 다음 네 가지 성공/실패 요청을 캡처해 여기에 결과를 옮깁니다.

- 로그인 없이 `/api/private`
- 계정 A/B 상호 자료 접근
- 사용한 challenge 재전송
- 패스키 삭제 후 삭제된 credential 로그인

### ⑤ AI와 나

AI는 요구사항 분해, WebAuthn/API/DB 구조 설계와 코드 초안을 담당했습니다. 실제 패스키 저장 위치 선택, 실제 두 기기/인증기 등록, Production 요청·응답 확인은 사용자가 직접 수행합니다.

### ⑥ 아직 못 막은 것

`attestation: none`이므로 인증기 제조사나 승인 기기 여부를 attestation 인증서 체인으로 확인하지 않습니다. 또한 모든 패스키 보관 기기를 동시에 잃은 경우의 별도 계정 복구 기능은 아직 없습니다.
